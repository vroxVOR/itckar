## Key question 1 — Recommended data model and availability/slot algorithm (staff + resources + buffers + processing gaps + multi-service) and how Cal.com and others implement it

### Takeaway
No open-source scheduler I could inspect models "processing gaps" (colour: 30 min apply / 45 min free / 30 min finish) or non-staff resources natively; Cal.com models availability as *per-user* date ranges minus busy intervals, then intersects hosts and generates slots on a fixed interval grid, with buffers applied by widening busy intervals. The practical design for salons is to decompose each service into ordered *segments*, each of which claims a set of resources (staff, chair, room, device) for a time range, and to compute availability as the intersection of per-resource free ranges shifted by each segment's offset.

**Cal.com availability algorithm (code paths, read 2026-09-28)**
- Entry point is `AvailableSlotsService.getAvailableSlots()` in `packages/trpc/server/routers/viewer/slots/util.ts`; it is wrapped in `withSlotsCache(redisClient, this._getAvailableSlots)` which checks Redis before running `_getAvailableSlots` and stores the result with a TTL — [packages/trpc/server/routers/viewer/slots/util.ts](https://github.com/calcom/cal.com/blob/main/packages/trpc/server/routers/viewer/slots/util.ts)

- `calculateHostsAndAvailabilities` fetches, in parallel, all existing bookings for the event type in the window (`bookingRepo.findAllExistingBookingsForEventTypeBetween`, with `seatedEvent: Boolean(eventType.seatsPerTimeSlot)`) and out-of-office days; parses `bookingLimits`/`durationLimits` JSON and converts limit breaches into synthetic busy times via `LimitManager`; then calls `userAvailabilityService.getUsersAvailability({ afterEventBuffer, beforeEventBuffer, duration, ... })` — [util.ts](https://github.com/calcom/cal.com/blob/main/packages/trpc/server/routers/viewer/slots/util.ts)

- `buildDateRanges` / `processWorkingHours` in `packages/features/schedules/lib/date-ranges.ts` iterate day by day in the organizer's timezone; the code explicitly computes `offsetDiff = start.utcOffset() - offsetBeginningOfDay` with the comment "there will be 60 min offset on the day of DST change", and notes "We only allow users to set availability up to 11:59PM which ends up not making them available up to midnight". Date overrides are processed with a ±1 day window (comment dated 2024-02-20 admits "mismatches between local and UTC dates for overrides"). The file also exports `intersect(ranges[][])`, `subtract(source, excluded)` and `mergeOverlappingRanges` — [date-ranges.ts](https://github.com/calcom/cal.com/blob/main/packages/features/schedules/lib/date-ranges.ts)
- Busy times (`packages/features/busyTimes/services/getBusyTimes.ts`) come from `status: ACCEPTED` bookings the user owns *or attends*, widened by buffers: `minutesToBlockBeforeEvent = (eventType.beforeEventBuffer||0) + (afterEventBuffer||0)` and `minutesToBlockAfterEvent = (eventType.afterEventBuffer||0) + (beforeEventBuffer||0)`; seated bookings are "non-blocking until the event is fully booked" and then only the buffer edges are busy; the booking being rescheduled is excluded (`rest.uid === rescheduleUid`); calendar busy times are widened `start.subtract(afterEventBuffer)` / `end.add(beforeEventBuffer)`. A `FIXME` says "bookings that overlap on one side will never be counted" for limit checks — [getBusyTimes.ts](https://github.com/calcom/cal.com/blob/main/packages/features/busyTimes/services/getBusyTimes.ts)
- Multi-host aggregation (`getAggregatedAvailability.ts`): fixed hosts (or all hosts for COLLECTIVE) are **intersected**; round-robin hosts are grouped by `groupId` and "at least one host from each group needs to be available" (union within a group, intersection across groups) — [getAggregatedAvailability.ts](https://github.com/calcom/cal.com/blob/main/packages/features/availability/lib/getAggregatedAvailability/getAggregatedAvailability.ts)
- Slot generation (`packages/features/schedules/lib/slots.ts`, `buildSlotsWithDateRanges`): picks the grid `interval` as the largest of `[60,30,20,15,10,5]` that divides `frequency` (else `NEXT_PUBLIC_AVAILABILITY_SCHEDULE_INTERVAL` or 1); converts to the *booker's* timezone before rounding ("prevents issues with half-hour offset timezones like Asia/Kolkata"); rounds the start up to the grid (or, with `showOptimizedSlots`, shifts only when spare minutes allow, to prefer :00/:15/:05 starts); walks `while (slotStart + eventLength - 1s <= range.end)` stepping `frequency + offsetStart`; deduplicates by ISO key; tags slots with OOO "away" metadata — [slots.ts](https://github.com/calcom/cal.com/blob/main/packages/features/schedules/lib/slots.ts)
- Soft holds: `_getReservedSlotsAndCleanupExpired` removes expired `SelectedSlots` and filters slots reserved by *other* booker uids; `reserveSlot.handler.ts` upserts a `SelectedSlots` row per host user with `releaseAt = now + MINUTES_TO_BOOK`, refuses if `findReservedByOthers` finds a live hold, skips holds for seated events unless the last seat, and sets a `uid` cookie with `SameSite=None; Secure` so embeds in third-party iframes work — [reserveSlot.handler.ts](https://github.com/calcom/cal.com/blob/main/packages/trpc/server/routers/viewer/slots/reserveSlot.handler.ts), [PrismaSelectedSlotRepository.ts](https://github.com/calcom/cal.com/blob/main/packages/features/selectedSlots/repositories/PrismaSelectedSlotRepository.ts)

- Cal.com's product blog describes "Optimized Slots" (the `showOptimizedSlots` flag above) — [Cal.com blog](https://cal.com/blog/optimized-slots-calcom-scheduling) [snippet]

### Inferences
- Cal.com's engine is *person-centric* (host = user with credentials); it has no notion of rooms/chairs/equipment. For a salon, generalise "host" to a `resource` entity with `kind ∈ {staff, room, chair, device}` and give every resource its own schedule + busy set; staff-only concepts (calendar credentials, OOO) hang off `staff`.
- Processing gaps: model a `service` as an ordered list of `segments` `{ offset_min, duration_min, requires: [resource_role...], blocks_staff: bool }`. For "colour": seg1 0–30 (stylist+chair), seg2 30–75 (chair only, stylist free), seg3 75–105 (stylist+chair). Availability for a start `t` = ∧ over segments of "every required resource free on [t+offset, t+offset+duration)". Persist one `appointment_segment` row per (segment × resource) with a `tstzrange` so DB constraints (Q2) apply per resource; the stylist's seg2 gap is simply *not* a row, so another 45-min service can be booked into it.
- Multi-service / multi-staff bookings are the same thing as several segments with different `requires`; a "basket" of services becomes one appointment with segments chained by cumulative offset (plus per-service buffers).
- Buffers should live on the *service* (before/after) and optionally on the *staff* (personal turnaround), applied by widening busy intervals exactly as Cal.com does, not by shrinking free ranges — this keeps the same code path for calendar busy times.
- Slot grid: copy Cal.com's approach (grid interval independent of duration, round to booker's tz, `minimumBookingNotice`), but add a tenant-level `slot_interval` default (5/10/15 min) because salons care about tight packing more than round starts; Easy!Appointments' 15-minute default is the common baseline.
- Capacity/classes: Cal.com `seatsPerTimeSlot` + `BookingSeat` (attendee-level rows, non-blocking until full) is the cleaner pattern versus Easy!Appointments' count queries; for group classes use a `class_occurrence` row with `capacity` and count confirmed seats.
- Recurring appointments: store the RRULE + timezone on a `series` row and *materialise* occurrences into real appointments for a rolling horizon (e.g. 6–12 months) so exclusion constraints and reminders work per occurrence; keep `exdates` for skipped/moved occurrences (rrule supports exdate/rdate).
- Time zones / DST: store all instants as `timestamptz`; store availability rules as local wall-clock time + IANA zone (as Cal.com does with `@db.Time` + `Schedule.timeZone`), and expand per-day in the zone (Cal.com's explicit DST offset handling shows why). Salons are single-location, so the tenant's location timezone is the organizer tz; the booker tz matters only for display.
- Performance: precompute/cached per-resource busy intervals per day (Cal.com's Redis cache of the whole slots response is coarse; a finer cache keyed by `(tenant, resource, day)` invalidated on write is easier to keep correct). Fetching bookings once for the whole window and doing interval arithmetic in memory (Cal.com's design) is fine up to thousands of bookings per query.
- Waitlists: not present in Cal.com or Easy!Appointments source I read; implement as `waitlist_entry {tenant, client, service, staff?, window tstzrange, created_at}` and fire on `appointment.cancelled` events (Cal.com's webhook trigger list has `BOOKING_CANCELLED` which is the analogous hook).

## Key question 2 — Preventing double bookings under concurrency in PostgreSQL (exclusion constraints, advisory locks, serializable transactions) with concrete SQL

### Takeaway
PostgreSQL's `EXCLUDE USING GIST (resource_id WITH =, during WITH &&)` (with `btree_gist`) is the only mechanism that makes overlap-freedom a database invariant under arbitrary concurrency; Cal.com does *not* use it and instead relies on a pre-insert re-check plus catching Prisma's `P2002` unique-violation and mapping it to HTTP 409, which only protects exact-duplicate slots, not partial overlaps.

### Cited Findings
- PostgreSQL manual, "Constraints on Ranges": "While UNIQUE is a natural constraint for scalar values, it is usually unsuitable for range types. Instead, an exclusion constraint is often more appropriate… Exclusion constraints allow the specification of constraints such as non-overlapping on a range type." Example: `CREATE TABLE reservation (during tsrange, EXCLUDE USING GIST (during WITH &&));` then inserting `'[2010-01-01 11:30, 2010-01-01 15:00)'` and `'[2010-01-01 14:45, 2010-01-01 15:45)'` yields `ERROR: conflicting key value violates exclusion constraint "reservation_during_excl"` — [PostgreSQL docs: Range Types §8.17.10](https://www.postgresql.org/docs/current/rangetypes.html) (read from the docs source [doc/src/sgml/rangetypes.sgml](https://github.com/postgres/postgres/blob/master/doc/src/sgml/rangetypes.sgml))
- Same section: "You can use the btree_gist extension to define exclusion constraints on plain scalar data types, which can then be combined with range exclusions… the following constraint will reject overlapping ranges only if the meeting room numbers are equal: `CREATE EXTENSION btree_gist; CREATE TABLE room_reservation (room text, during tsrange, EXCLUDE USING GIST (room WITH =, during WITH &&));`" with the demonstrated conflict for room `123A` and success for `123B` — [PostgreSQL docs: Range Types](https://www.postgresql.org/docs/current/rangetypes.html)
- PostgreSQL manual, "Exclusion Constraints": "Exclusion constraints ensure that if any two rows are compared on the specified columns or expressions using the specified operators, at least one of these operator comparisons will return false or null… Adding an exclusion constraint will automatically create an index of the type specified in the constraint declaration." — [PostgreSQL docs: DDL Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (source [ddl.sgml](https://github.com/postgres/postgres/blob/master/doc/src/sgml/ddl.sgml))
- btree_gist also indexes `<>`, enabling constraints like `EXCLUDE USING GIST (cage WITH =, animal WITH <>)` — [PostgreSQL docs: btree_gist](https://www.postgresql.org/docs/current/btree-gist.html) (source [btree-gist.sgml](https://github.com/postgres/postgres/blob/master/doc/src/sgml/btree-gist.sgml))
- Range bounds: inclusive lower bound `[`, exclusive upper bound `)`; every range type has a multirange (`tstzmultirange`) — [PostgreSQL docs: Range Types](https://www.postgresql.org/docs/current/rangetypes.html)
- Practitioner articles show the partial-constraint variant `EXCLUDE USING GIST (resource_id WITH =, tstzrange(start_time,end_time,'[)') WITH &&) WHERE (status = 'confirmed')` so cancelled/tentative rows do not block, and note half-open `'[)'` lets 10:00–12:00 and 12:00–14:00 coexist — [dev.to: Preventing double-bookings with PostgreSQL exclusion constraints](https://dev.to/ripazocom/preventing-double-bookings-with-postgresql-exclusion-constraints-5efn) [snippet]; [jusdb blog](https://www.jusdb.com/blog/postgresql-range-types-exclusion-constraints) [snippet]; [boringSQL: Beyond Start and End](https://boringsql.com/posts/beyond-start-end-columns/) [snippet]
- Cal.com booking write path: `createBooking.ts` wraps the insert in `prisma.$transaction(async (tx) => { const booking = await tx.booking.create(createBookingObj); ... })`; `RegularBookingService.ts` catches the error and `if (err.cause.code === "P2002") throw new HttpError({ statusCode: 409, message: ErrorCode.BookingConflict })` — [createBooking.ts](https://github.com/calcom/cal.com/blob/main/packages/features/bookings/lib/handleNewBooking/createBooking.ts), [RegularBookingService.ts](https://github.com/calcom/cal.com/blob/main/packages/features/bookings/lib/service/RegularBookingService.ts)
- Cal.com's pre-insert check `ensureAvailableUsers` recomputes each user's date ranges and buffered busy times for the exact requested window and rejects with `ErrorCode.NoAvailableUsersFound`; `checkForConflicts()` sorts busy intervals and returns true if any `busy.start < slotEnd && busy.end > slotStart` (seated slots with existing seats are exempt) — [ensureAvailableUsers.ts](https://github.com/calcom/cal.com/blob/main/packages/features/bookings/lib/handleNewBooking/ensureAvailableUsers.ts), [checkForConflicts.ts](https://github.com/calcom/cal.com/blob/main/packages/features/bookings/lib/conflictChecker/checkForConflicts.ts)
- Cal.com's only DB-level uniqueness on bookings is `uid @unique`, `idempotencyKey String? @unique` (comment: "UID based on slot start/end time & email against duplicates") and `oneTimePassword @unique`; there is no exclusion constraint in `schema.prisma` — [schema.prisma](https://github.com/calcom/cal.com/blob/main/packages/prisma/schema.prisma)
- Cal.com product-side mitigation: PR "Introduce a 'slot no longer available' message" and issues about slots offered that fail at submit ("No available users found") show the check-then-insert race surfaces to users — [PR #18935](https://github.com/calcom/cal.diy/pull/18935) [snippet], [Issue #30195](https://github.com/calcom/cal.diy/issues/30195) [snippet]

### Inferences
- Recommended schema (my synthesis of the PostgreSQL docs above; SQL follows the documented syntax):
  ```sql
  CREATE EXTENSION IF NOT EXISTS btree_gist;
  CREATE TABLE appointment_segment (
    id            bigserial PRIMARY KEY,
    tenant_id     uuid NOT NULL,
    appointment_id uuid NOT NULL,
    resource_id   uuid NOT NULL,          -- staff, chair, room or device
    during        tstzrange NOT NULL,     -- '[)' half-open, buffers already included
    status        text NOT NULL,          -- 'hold' | 'confirmed' | 'cancelled' ...
    EXCLUDE USING GIST (tenant_id WITH =, resource_id WITH =, during WITH &&)
      WHERE (status IN ('hold','confirmed'))
  );
  ```
  Including `tenant_id` in the exclusion is cheap and keeps the index tenant-local; the `WHERE` clause lets cancelled rows stay for history.
- For capacity (classes) an exclusion constraint cannot express "≤ N overlapping"; use a `class_occurrence` row with `capacity` and insert seats under `SELECT … FOR UPDATE` on that row (or `pg_advisory_xact_lock(hashtext(occurrence_id))`) and check `count(*) < capacity` in the same transaction.
- Holds: Cal.com's `SelectedSlots` with `releaseAt` is an application-level lock with a TTL. With exclusion constraints you can instead insert `status='hold'` segment rows with an `expires_at` and a sweeper; a confirmed insert then races only against live holds, and the constraint arbitrates.
- Idempotency: adopt Cal.com's `idempotencyKey` idea but make it mandatory for public API writes (`Idempotency-Key` header → unique index on `(tenant_id, key)`); return the original response on replay. The exclusion violation (SQLSTATE 23P01) and unique violation (23505) should map to HTTP 409 with a machine-readable code, and the client should refetch slots.
- Serializable isolation is a workable alternative for a low-write system (retry on SQLSTATE 40001) but gives no invariant if any code path bypasses it; advisory locks per resource serialise writers without an index but also give no invariant. Exclusion constraints are the only option that survives bugs in application code, so use them as the backstop and keep the fast pre-check for good UX.
- Optimistic locking (`version` column) is for *updates* (reschedule/edit by two receptionists), not for insert races; combine: `UPDATE … WHERE id=? AND version=?` and re-insert segments in the same transaction so the exclusion constraint re-validates the new time.

### Gaps
- I could not open the PostgreSQL manual's `CREATE TABLE` page to quote the exact `EXCLUDE … WHERE (predicate)` grammar; the partial-constraint syntax is confirmed only via practitioner articles [snippet] and my knowledge that `EXCLUDE` accepts a `WHERE` predicate.
- No benchmark source for GiST exclusion-constraint insert throughput at salon scale was found; the assertion that it is adequate is inference.

## Key question 3 — Which multi-tenancy pattern fits a solo/small-team SaaS with EU customers, and why

### Takeaway
Shared schema with a `tenant_id` column on every table plus PostgreSQL row-level security (and `tenant_id` in every composite key/index) is the pattern recommended by Citus/Supabase documentation and practitioner guides for many small tenants; schema-per-tenant and DB-per-tenant trade operational pain (migrations × N, connection-pool pressure, catalog bloat) for isolation that RLS already gives at the row level.

### Cited Findings
- Citus multi-tenant guide: "each tenant's data can be stored together in a single database instance and kept isolated from and invisible to other tenants… application improvements apply to all clients… sharing a database between tenants uses hardware efficiently… it is much simpler to manage a single database"; every table gets a tenant column (`company_id`) used as the distribution column; "Citus requires that primary and foreign key constraints include the distribution column", i.e. composite keys `(company_id, id)`; "Even in a single-machine database it can be useful to denormalize tables with the addition of company id, whether it be for row-level security or for additional indexing"; per-tenant custom fields via JSONB; tenant sizes follow a Zipfian distribution ("in a database of 100 tenants, the largest is predicted to account for about 20% of the data… if there are 10k tenants, the largest will account for around 2%"); big tenants can be isolated with `isolate_tenant_to_new_shard` — [Citus docs: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html) (read from [citus_docs source](https://github.com/citusdata/citus_docs/blob/master/use_cases/multi_tenant.rst))
- Supabase RLS guide: "Think of a policy as adding a WHERE clause to every query"; write separate policies per operation (`for all` "hides which operation each rule was meant to cover"); an `UPDATE` policy needs a matching `SELECT` policy; wrap helper calls as `(select auth.uid())` for performance; **views bypass RLS by default** because they are created `security definer`; `service_role` bypasses RLS "so keep it server-side"; test policies with `set local role authenticated; set local request.jwt.claim.sub = '…'` — [Supabase docs: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security) (read from [source mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/database/postgres/row-level-security.mdx))
- Practitioner comparison: RLS "guarantees at the database level that cross-tenant data access cannot happen"; schema-per-tenant "does not meaningfully impact data isolation from a security perspective" and "doesn't scale past ~100 tenants… with 10,000 clients and 50 tables, you have 500,000 files in the database directory"; more schemas → more catalog memory and connection-pool pressure; DDL must loop over all tenants — [dev.to: RLS vs schema-per-tenant](https://dev.to/itsjayanth/multi-tenant-postgresql-row-level-security-vs-schema-per-tenant-when-to-use-which-3joe) [snippet]; [PlanetScale: Approaches to tenancy in Postgres](https://planetscale.com/blog/approaches-to-tenancy-in-postgres) [snippet]
- Cal.com (a mature scheduling SaaS) uses a single shared Postgres schema with `teamId`/`userId`/organization foreign keys and no RLS in its Prisma schema; isolation is enforced in application code — [schema.prisma](https://github.com/calcom/cal.com/blob/main/packages/prisma/schema.prisma)
- Cal.com API v2 (NestJS) uses `@nestjs/throttler` with `@nest-lab/throttler-storage-redis` for per-client rate limiting — [apps/api/v2/package.json](https://github.com/calcom/cal.com/blob/main/apps/api/v2/package.json)

### Inferences
- For a 1–3 person team: one Postgres cluster in an EU region, one schema, `tenant_id uuid NOT NULL` on every business table, composite unique keys `(tenant_id, …)`, and RLS `USING (tenant_id = current_setting('app.tenant_id')::uuid)` set with `SET LOCAL` at the start of each request transaction. Run application queries under a non-superuser role that does **not** own the tables (owners bypass RLS) and keep a separate `admin`/migration role.
- Pooling: `SET LOCAL` (transaction-scoped) is required with transaction-mode poolers (PgBouncer/Supavisor/Neon's pooler) because session-level `SET` leaks across pooled connections.
- Exclusion constraints and RLS compose fine; include `tenant_id` in the exclusion (Q2) so the GiST index is partitioned logically by tenant.
- Reserve schema-per-tenant/DB-per-tenant only for a future "enterprise chain" tier (e.g. a 50-location franchise wanting its own backups/export); Citus tenant isolation or a second cluster can serve that without changing code if `tenant_id` is everywhere from day one.
- GDPR benefit: a shared schema with `tenant_id` makes tenant export/delete a set of `WHERE tenant_id = ?` operations; DB-per-tenant makes deletion trivial but backup/restore and PITR per tenant expensive on managed platforms (Supabase PITR is priced per project, see Q7).

### Gaps
- I found no public statement from Fresha, Booksy or Zenoti on their tenancy model. The claim "what mature booking SaaS use" is therefore supported only by Cal.com's open schema (shared, app-enforced) and generic guidance.
- The AWS SaaS Lens and Crunchy Data RLS articles suggested in the brief were not reachable; their content is not represented.

## Key question 5 — Stripe Connect vs. local gateways for CZ/SK: fees, deposits, card-on-file no-show fees, payouts, Apple/Google Pay, terminals

### Takeaway
Stripe's EEA card pricing (1.5% + €0.25 standard / 1.9% premium / 2.5% UK / 3.25% international, dispute €20 = 550 Kč non-refundable) is materially higher than Czech gateways' headline rates (Comgate Profi 0.67% + 1 Kč; GoPay ≈0.95%), but Stripe alone was documented as offering the full platform toolkit a booking SaaS needs — Connect onboarding/payouts to each salon, SetupIntents for card-on-file, off-session merchant-initiated charges for no-show fees, and Terminal hardware — so the usual answer is Stripe Connect for the platform features with local gateways as a cheaper option only if you build the money flows yourself.

### Inferences
- Deposit flow: create a PaymentIntent for the deposit (with `setup_future_usage: off_session` so the same card can be charged for a no-show), or a SetupIntent only ("card required, nothing charged"). No-show: create a PaymentIntent `off_session: true, confirm: true` against the saved payment method; handle `authentication_required` by emailing/SMS-ing a pay link (Stripe's documented fallback). Cal.com's `PaymentOption.HOLD` is the same product idea.
- With Connect, use *destination charges* (platform collects, transfers to the salon's connected account) if you want to take a platform fee and control refunds/no-show disputes; Express onboarding gives salons a Stripe-hosted dashboard for payouts. Standard accounts cost nothing extra but push KYC/dashboard to the salon and make the salon the merchant of record.
- Fee arithmetic for a 1,200 CZK service paid by a Czech consumer card: Stripe ≈ 1.5% × 1,200 + 6.50 = 24.50 Kč (≈2.0%); Comgate Profi ≈ 0.67% × 1,200 + 1 = 9.04 Kč (≈0.75%); GoPay ≈ 11.40 Kč. - Apple Pay/Google Pay are included in Stripe card pricing; all major CZ gateways advertise them, but tokens for *later* off-session charging are the differentiator to verify.
- Accounting exports: none of the sources covered it; plan a per-tenant CSV/ISDOC export and a Stripe/Comgate settlement reconciliation job (payout id ↔ appointments).

### Inferences
- Licensing posture: (a) Cal.diy (MIT) can be forked, modified and hosted commercially without source-disclosure obligations, but lacks Teams/Organizations/Workflows — the very features a multi-tenant salon SaaS needs; (b) using Cal.com proper (AGPLv3 core + commercial `ee`) as the base of a closed SaaS would require either publishing your modifications to users (AGPL §13, network use) or buying Cal.com's platform license; (c) Twenty/Documenso/Rallly/Hi.Events are AGPLv3 — fine as *inspiration* and for self-hosted internal tooling, not as embedded code in a proprietary product; (d) GPLv3 (Easy!Appointments, Alf.io) has no network clause, so *hosting* modified versions without distributing binaries does not trigger source release, but linking their code into your product would.

## Key question 7 — Realistic MVP architecture, 6–9 month roadmap for a small team, and monthly infra costs at 100 / 1,000 / 10,000 tenants (incl. calendar sync, messaging, AI receptionist, GDPR, i18n, embeds, testing)

### Takeaway
A pragmatic stack is the one Cal.com already validates in production — TypeScript monorepo (Next.js + tRPC or NestJS API), Prisma or Kysely over PostgreSQL in an EU region, Redis for caching/queues, a DB-backed job queue with cron — plus exclusion constraints and RLS that Cal.com lacks; infra for 100 tenants fits in ~€50–150/month, 1,000 tenants in ~€300–800/month, and 10,000 tenants in ~€2–5k/month before messaging/AI usage fees, which will dominate at scale.

**Embeds, GDPR, accessibility**
- Iframe vs Shadow DOM: iframes give hard isolation but "are inherently unresponsive and require postMessage-driven mechanisms to manually keep height up to date", slower init (separate document + assets), CORS/scroll awkwardness; Shadow DOM web components give CSS encapsulation "without limiting your ability to have control", support CSS custom properties/dark mode, but share the host's JS realm — [Medium: Shadow DOM vs iFrame](https://medium.com/@blue___gene/shadow-dom-vs-iframe-a-philosophical-and-practical-exploration-of-embedding-on-the-web-c5369031e54d) [snippet]; [BBC: Goodbye iframes](https://medium.com/bbc-product-technology/goodbye-iframes-6c84a651e137) [snippet]; [Webagility](https://www.webagility.com/posts/web-components-vs-iframes) [snippet]; Cal.com's production embed is iframe + `postMessage` height sync with a Shadow-DOM loader — [embed-core README](https://github.com/calcom/cal.com/blob/main/packages/embeds/embed-core/README.md)

### Inferences
- **MVP architecture (single region, EU):** Postgres 16/17 (Neon or Supabase in Frankfurt, or self-managed on Hetzner Falkenstein with pgBackRest/WAL-G) with `btree_gist` exclusion constraints and RLS; Redis (Upstash or self-hosted) for slot cache + rate limits; a DB-backed job table + cron worker (Cal.com Tasker pattern) for reminders, calendar sync, webhooks, with BullMQ only if you need sub-minute latency; Next.js (booking pages + admin) + tRPC for the first-party app and a small NestJS/Hono REST API with OpenAPI for partners/webhooks (Cal.com's split); Prisma for migrations + Kysely for the availability queries (Cal.com generates both from one schema); Expo/React Native for the staff app (same TS types via the API); Stripe Connect Express for payments; SES/Resend for e-mail; a CZ SMS gateway (BulkGate/GoSMS) for CZ/SK numbers with Twilio as fallback; WhatsApp via Meta Cloud API once templates are approved; Vapi/Retell/ElevenLabs Agents calling your `find_slots` / `book` / `cancel` tools over HTTPS for the AI receptionist (they already provide the telephony + STT + TTS loop).
- **Roadmap (2–3 engineers, 6–9 months):** M1–2 engine + admin calendar (services with segments, resources, staff schedules/exceptions, exclusion constraints, holds, reminders by e-mail/SMS, hosted booking page, i18n cs/sk/en); M3 payments (Stripe Connect onboarding, deposits, card-on-file no-show fees, POS via Terminal or "pay in salon" recording), client CRM + GDPR export/delete, audit log; M4 Google/Microsoft calendar 2-way sync + iCal feeds, embeddable iframe widget + custom domains; M5 public API + webhooks, Reserve with Google Business Link, WhatsApp utility templates; M6 mobile staff app (Expo), reports/accounting exports; M7–9 AI receptionist (chat first, voice second), no-show scoring (start with rules: prior no-shows, lead time, new client, unpaid deposit), marketing automations, RwG end-to-end, Meta Book Now application. Testing the engine: property-based tests over random schedules asserting "no returned slot conflicts with any busy interval or exclusion constraint", golden tests around DST transition days (last Sunday of March/October, Europe/Prague), and integration tests that fire concurrent booking requests at the same slot and assert exactly one 2xx.
- **Cost model (my estimate from the cited prices; excludes messaging/AI usage and VAT):**
  - ~100 tenants (≈300 staff, ≈30k appointments/month): Neon Launch or Supabase Pro + Small compute ≈ $25–60; app on Hetzner CX23/CX33 ×2 ≈ €12–25 or Vercel Pro $20/seat; Redis (Upstash pay-as-you-go) ≈ $0–10; SES ≈ $5; backups/object storage ≈ $5; Sentry/PostHog free tiers → **≈ €60–150/month**. SMS at ~1 reminder/appointment ≈ 30k × 0.8 Kč ≈ 24k Kč/month is already the largest line if you pay it rather than pass it through.
  - ~1,000 tenants (≈300k appointments/month, ~10–50 GB DB, few hundred req/s peaks): Supabase Pro + Large/XL compute ($110–210) + PITR $100, or Neon Scale ≈ 2–4 CU always-on (≈ $320–640/month) + storage; 2–3 app nodes (Hetzner CPX/CCX ≈ €50–150) or Vercel Pro + functions; managed Redis $20–50; e-mail $30–60; monitoring $50–100 → **≈ €400–1,000/month**.
  - ~10,000 tenants (≈3M appointments/month, hundreds of GB, calendar-sync fan-out): dedicated Postgres 8–16 vCPU (Supabase 2XL–4XL $410–960 or self-managed HA pair on Hetzner dedicated ≈ €150–300 + ops time) + read replica, Redis cluster, 4–8 app/worker nodes, object storage, Team-tier compliance (Supabase Team $599 or Neon Scale) → **≈ €2,000–5,000/month** infra; messaging (3M SMS ≈ 2.4M Kč ≈ €95k/month if SMS-first, far less with WhatsApp utility/e-mail/push) and AI voice minutes ($0.13–0.32/min) will exceed infra by an order of magnitude and must be metered per tenant.
